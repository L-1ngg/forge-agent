## F.0 怎么读这份材料

本项目适用范围(2026-09-06):F.8 的旧阶段映射保留为历史,当前行动项见 [plan.md](plan.md)。Team 归外部项目、自研内核与输入生命周期分别以 ADR-008/009/010 为准。F.5 的工具教训不是全面禁止 MCP;压缩阈值与记忆机制也只是研究建议,不能视为已实现能力。下文证据标签与源锚点保持原含义。

| 标签 | 含义 | 可信度 |
|---|---|---|
| `[明述]` | 文档里直接写了这句话 / 这个数字 | 高 |
| `[自证]` | 文档 A 声称有某能力,文档 B 的施工记录否证了它;以施工记录为准 | 高(比明述更硬) |
| `[推断]` | 由调研过程从症状推出,文档没这么说 | 中,**不可当事实引** |
| `[弱证]` | 有正面案例,但样本或压测不足 | 低,**不可用于反驳相反方案** |

**先做一次适用性折扣:** 他们的核心痛苦来自**包裹三个自己不控制的外部 CLI**(Claude Code / Codex / Gemini),本项目自己拥有压缩调用点和 tool-call 循环。凡是根源在「进程外」的教训,先判断是否还成立——一半的工程量对本项目不存在。

**已修正的两处我方误判**(以免后续再引错):`06-vanished-28-seconds.md` 是 **Redis 数据丢失复盘**(28 秒 = 两次 RDB 快照之间的空档,307 → 144 keys),不是延迟 / 流式故事;`15-why-still-running.md` 是**「项目跑了 54 天没烂掉」的治理复盘**,不是进程生命周期 bug。`03-meta-rules.md` 也不是「关于规则的规则」,是「**从 AI 弱点反推出的规则**」(幻觉 / 讨好 / 缺乏持久记忆 / 过度自信 → 五条元规则,`03:104-289`;「讨好」一个弱点派生出两条)。

## F.1 改设计的六条(按代价排序)

### ① 原始需求原文必须进 slot,和身份同级 `[明述]`

F041:12 条 AC 全绿、76 测试 0 失败、14 轮 review、已合入 main(`09:30-34`)。铲屎官打开产品 **5 秒**发现四个问题(没有描述、分组维度错、多项目管理完全没做、来源分类错,`09:90-103`)——而这四条在原始 Discussion 里都明确写了。六份独立调研 + GPT-5.2 Pro 仲裁(`09:178`)收敛到同一句:**整条 review 链路没有任何角色回去读用户的原始需求**(`09:182`)。 10 轮云端 review 全在抓 edge case,没有一轮说「UI 太丑了」或「多项目管理呢」。⚠️ 原文自身口径矛盾:摘要写 14 轮,正文是本地 2 轮 + 云端 10 轮 = 12(`09:81, 09:133`);引用时用「12+ 轮」更稳。

> 命题:**AC 是需求的有损压缩。** 一旦写好,全链路只看 AC。

本项目 pre-compact 载荷里的「任务摘要」就是 AC。

**动作:把用户原始请求的原文(不是摘要)钉进一个 slot,和 `IDENTITY.md` 一样放 transcript 之外,压缩吃不掉。** → plan Phase 3

附带同源约束:**关联错误** `[明述]`(`09:458-470`)。14 轮 review 共享同一份上下文、缺失同一份信息,是完全关联的错误;完全关联下 10 轮之后正确率还是 0.95,第 14 轮和第 1 轮价值相同。「数量不能修复方向偏差。」→ 恢复路径的质量下限由**载荷内容**决定,不由注入次数或注入可靠性决定。

### ② 阈值必须留余量,且要在真相点计算 `[明述]`

他们的 seal 阈值 0.90,而外部 CLI 自动压缩约 0.95 触发,中间只有 5% 窗口(`08:290`)。原文:**「布偶猫从未成功在 CLI 压缩前完成交接。」**(`08:293`,F24 的 seal 机制对布偶猫独立 session 几乎失效。)机制存在,一次也没跑起来过。修法是 `shouldTakeAction()`,预警 0.80 / 动作 0.88(`08:317-355`)。⚠️ 0.80/0.88 是 F33 时代**布偶猫 breed 级**配置,不是全局值(缅因猫是 0.75/0.90,`08:365`;F24 时代是 85/90,`08:211`)——引用时说明是哪个阶段。

同一事故里前端健康条显示 82%,真实已 95%——因为那是上一次调用的缓存快照(`08:128-129`)。

**动作:写出触发留足余量(0.80 / 0.88);TUI 的 context 用量在真相点计算,不展示残留值。** → plan Phase 2(status line)+ Phase 3

### ③ 授权必须连同它的对象一起被验证 `[明述]`

design-rationale B 原本要原文抄的那句是「不要假设用户批准过任何操作,除非在当前 context 里找到明确证据」。F24(源文档两位数编号,`08:132-137`;故事在 08 课不在 09 课)恰好是它的反例:压缩后 agent 从摘要里读到「铲屎官说可以合入」——**这句话是真的,但它是关于 PR #1 的**。压缩丢掉的是作用域,不是授权本身。于是 `gh pr merge 3 --squash`。

模型确实找到了显式证据,所以原措辞挡不住 F24。

**动作:措辞改成「任何授权必须连同它的对象一起被验证」。** → design-rationale B

### ④ 状态文件是本项目唯一的 out-of-band key `[明述]` + `[推断]`

他们提炼出 **Thread Affinity**:「任何有状态的对象,如果它应该属于某个 thread,必须显式绑定 threadId。**不存在『默认绑定到当前 thread』这种安全假设。**」(`08:397`)三个 bug 同一形状:

- 茶话会夺魂 —— session resume key 写成 `userId:catId`,缺 threadId(`08:65`),于是 `codex exec resume X` 把 Phase 5 的完整上下文装进了一场只能聊天的茶话会(`08:72`;CLI 是 codex)
- timer 串线、socket summary 漂移 —— 两个修复都是一行 `if (event.threadId !== currentThreadId) return`(`08:390-400`)

本项目的 `id` / `parentId` 内嵌在 entry 里,没有外部 key 可写错,**树形单文件在结构上免疫了他们的头号 bug** `[推断,已审:成立但限定范围——免疫的是 resume-key 类 bug]`。但 pre-compact 写出的状态文件如果只按 session 命名,同一 session 分了两个分支各自压缩过,SessionStart 就可能注入另一条分支的状态,症状同样诡异(agent 谈论本分支从没发生过的事)`[推断,已审:状态文件仍是 out-of-band key,下面的动作即为此而设]`。

**动作:状态文件的 key 带写出时的 head entry id;SessionStart 校验它是当前 head 的祖先,否则丢弃。** → plan Phase 3

同节还有一条可直接借的判据 `[明述]`(`08:88-99`):他们的 HOME 隔离方案 6 个 commit **全部回退**(`auth.json` 被重建覆盖 → 401;`config.toml` 被覆盖 → 模型回落;`sessions/` symlink 失败 → resume 找不到;MCP servers 丢失;project trust 丢失),而根因修复其实是两行(key 加 threadId,`08:78`)。

> **补丁数量是方案质量的信号。**(`08:99`)配套:区分根因和触发器。

### ⑤ 按需拉取几乎总是优于一次性灌入 `[明述]`,但这条本身未被验证 `[空白]`

这是作者最推崇的一般化结论(`08:420`)。他们的 bootstrap packet 第 4 件东西是一条规则:不确定之前做了什么就先 `session_search(query)` → `read_session_events(view="handoff")` → `read_invocation_detail()`,**「不要猜。」**(`08:270-279`)`session_search` 被作者称为最关键的工具,类比是读旧 session 等于搜代码:grep → 定位 → 只读那一处(`08:261-264`)。

本项目的 transcript 就在本地 JSONL 里,加一个等价的本地搜索函数 + 写死那句规则几乎零成本。

**动作:载荷保持短 + 提供本地 `session_search` 等价函数 + 把「不要猜,去搜」写死进载荷。** → plan Phase 1(函数)+ Phase 3(载荷)

**重要限定:这批文档没有任何重新注入载荷的前后对比数据,也没报告任何注入失败模式**(`[空白]`,已审确认)——没有「agent 无视载荷」、没有「载荷太长」、没有「上下文重复」。所以他们的 bootstrap packet 只是**被设计过**,不是被验证过。被验证失败的是 ② 的阈值。

### ⑥ 濒死猫写不好遗书 —— 已规避,但要顺审一遍 `[明述]`

他们否掉了「让快满的 agent 写交接文档」,理由是 90% context 的模型自己已经记不清早期细节(`08:143-145`,出处在 08 课;原文无「动工之前」这个时间状语,只是叙事顺序上先否定再提 Sub-agent 尸检模式)。本项目的确定性 digest(`filesTouched` / `toolNames` / `errors` / 最近 N 条)正是这个批判的规避方式,**这是它的正面证据**。

**动作:六段载荷里任何需要模型自述或判断的部分,一律挪到读取时做。** → design-rationale B

## F.3 skill 与记忆:三处净增量

### 三件套缺一槽:副作用 `[明述]`

完整形态是 `what + when + not-when + side effects + output`,且**边界要写到 description,因为正文可能根本没被加载**(「description 写不好 = 正文永远不会被加载」,`09:253`)。惊吓型失败的例子:description 写「分析财报」,正文顺手发邮件通知 CEO(`res:knowledge-engineering-skills-mcp.md:140-141`)。⚠️ 出处修正:四字段(含 `Side effects: None` 必填)在 `res:templates.md:30,43`,第 10 课只有三件套(`10:285`)——这套纪律的真实来源是他们的 **research 报告**,不是 lessons。

**动作:skill 描述纪律改成 `Use when: / Not for: / Output: / Side effects:`,无副作用写 `none (read-only)`。** → design-rationale B

配套三条便宜的 `[明述]`(均出自 research 报告):反例要出现两次(description + 正文,`res:knowledge-engineering-skills-mcp.md:161`);示例集是边界训练集不是演示,每个 skill ≥2 正例 + 2 反例 + **1 灰例**(可以触发但要先问一个澄清问题,`:217-219`);迭代顺序是**先补反例 → 再补话术 → 最后才调 workflow**(`:389`)。以及人类代理测试:「把 10 条真实请求丢给同事,只看 description 选技能。他都选不稳,模型只会更不稳。」(`:208`)

三层加载的一句话总结:**description 写给路由,正文写给执行。**(「description 是给路由器看的分类器」,`10:441`)

### 合并有上限 `[明述]`

他们 25 → 15,但 GPT-5.2 驳回了继续合并 `quality-gate` + `request-review` + `receive-review`,理由是「触发时间天然不同:『我写完了』→ 自检、『自检过了』→ 发请求、『收到反馈了』→ 处理。合在一起会过度触发」。立下的硬规则:**合并后 description 若变成「什么都能做」就拆回去。路由精度 > skill 数量。**(均在 `09:305-333`,⚠️ 出处在 09 课不在 10 课)

铲屎官的原始需求之一是「怕以后有 100 个 Skills 烧上下文,需要控制每只猫加载哪些」(`09:60`,F041 的原始需求)——常驻 description 的总预算是真实约束,**per-profile skill allowlist 迟早需要**。

### 记忆:「何时写」是个错问题,该问准入 `[明述]`

7 槽模板(坑 / 根因 / 触发条件 / 修复 / 防护 / 来源锚点 / 原理,`10:325-337`)配三条门禁(`10:349-351`):

1. 至少 1 个可追溯锚点(`commit:sha` | `file#Lx` | doc 链接)
2. **「防护」字段必须是可执行机制** —— 「be careful」不合格,「跑 xxx 测试」合格
3. 「原理」只有在有真实失败案例支撑时才能填

> 「『注意』不是防护,『不要忘记』不是机制。」

它举的坏记录范本是这一句:**「注意不要在 compact 后忘记 identity 注入。」**(`10:342-344`)这几乎就是本项目的身份生存问题,而它被当成「三个月后完全看不懂」的反面例子。反过来强力支持本项目的决策:**把 identity 放 system-prompt slot、放 transcript 之外,正是这条坏教训所缺的那个「可执行防护」。**

**动作:把三条门禁做成写入准入检查——写不出锚点和可执行防护的就不许写。「何时写」自动被解决。** → plan Phase 3

## F.4 检索质量:比预期弱得多 `[弱证]`

他们建过语义检索的雏形(`semantic` 模式 + `EMBED_MODE=off/shadow/on` + fail-open,`14:96, 14:200-210`),但默认 off、从没压测过,也没报告任何 recall 失败的量化故事。⚠️ 原稿「从没建过语义检索层」不准确,已修正。日常检索栈就是 frontmatter 三字段 + `grep -rl "F021"` + 一个读 frontmatter 的 `feat_index` + 聚合文件当入口页(`10:168-209`)。

**不要把这当成「embedding 不必要」的证据:** 语料只有 707 个文档(`10:196`);检索单位是**整篇文档**(找到聚合文件就算成功),不是一条记忆条目;从没压测过;`bm25` 那种排序质量问题他们根本没进入过。

而他们对 recall 失败的三条诊断都不是排序问题:没 schema、没层次、**没生命周期**(`10:67-71`:文档只增不减 → 信噪比持续下降 → 最终没人看;`docs/discussions/` 30 个讨论 25 个已收敛,信噪比 17%,`10:219-221`)。

> 修法是**策展**而不是排序:按月 `git mv` 归档,「归档 ≠ 删除,历史有价值,但它不该出现在你日常浏览的活跃目录里」(`10:225-243`;「策展而非排序」是我们的概括,原文无此措辞)。

## F.5 MCP 的问题关掉了 `[明述]`

MCP 在他们体系里只干两件事:把 session 回忆工具箱暴露给**他们不控制的外部 CLI 进程**(`session_search` 等 MCP 工具,`08:218`);归一化三种 CLI 的配置(F043,`10:209, 10:527`)。⚠️ 审核修正:原稿把「F043」和「27 个 adapter 测试」拼成一件事——27 个 adapter 测试实际属于 F041 能力看板(`09:74`),与 F043 无关;且 05 课主题是 MCP 回传(post_message),不是这两件事的出处。本项目单进程、自己拥有 tool-call 循环,两件事都不存在——同样功能就是本地函数。代价只有一项:用不上别人写好的 MCP server。

**但那份研究报告里与协议无关的工具设计规则是纯收益(`res:knowledge-engineering-skills-mcp.md:300-321`、`res:templates.md:243-263`),直接进 `packages/tools`:**

- 能 `enum` 就别自由文本;能分类型就别混 `string`;`additionalProperties: false`;必填字段尽量少,但一旦必填就别留模糊空间
- 自测法:「把 schema 字段描述删掉只留类型,如果工具立刻变难用,说明描述本来就不够结构化」
- 错误返回统一含 `error_code`(稳定枚举)/ `message` / `field` / `expected` / `example` / `retryable`

> 「工具错误不是报错就完事,是模型下一次能不能改对的教材。」

顺带:他们也有 `pnpm check:skills`(Skill 挂载 + manifest 一致性,`10:254`,仅一行提及),但文档没写机制(已审确认)。所以**既不能证实也不能反驳**我对 clowder「排序后名字的 SHA-256 检测不到内容修改」的批评 —— 别当证据引 `[空白]`。

## F.6 design-rationale D 那条规则拿到了对方阵营的自证

`03-meta-rules.md` 明确声称 Skill 提供「**强制执行**:触发词匹配后自动执行检查」(`03:370`),并列了 `merge-approval-gate`(触发词「合入 main」,`03:341`),本篇内没承认任何执行力缺口 `[明述]`(系列层面是有自知的——09 承认了,只是 03 没有)。

`09` 自己把它推翻了 `[自证]`:三层防御表里,流程守护那行写的是「⚠️ 5 个 Skill 有对齐步骤 / ❌ **全是文字指令,无强制执行**」,技术嵌入那行是「❌ 完全空白」(`09:190-192`)。GPT-5.2 Pro 的评价:「鲁棒性**低到中——任务越长越低**」(`09:198-199`,原文自标 `[推断]`)。

更硬的是两次真实未授权合入 `[明述]`:F11(agent 自判改对了直接合入,`03:278-280`)、F24(压缩后误读授权,`08:132-137`)。⚠️ 审核修正:原稿写「`merge-approval-gate` 在场的情况下失守」——**对 F11 不成立**(F11 恰是制定该 gate 的教训来源,时间线上 gate 在事后才存在);F24(2026-02-15)时 gate 是否在场原文无法确证。真正过硬的证据是 09 的自证,不是「在场失守」。事后他们做了什么?**补了三层 Claude Code hooks 防线。**

> 所以「**一条规则一个家,且选那个能说「不」的家**」成立,而且论据现在是对方的施工记录,不只是我方推理。

**但他们有一处比我们好,值得拿:** `03` 把「放行」写成了**可机检的输出契约**,不是模糊规则。

- 有效放行白名单:`可以放行了` / `LGTM` / `通过`(`03:266-273`)
- 显式无效:`整体 OK,但 XXX 需要改`(条件放行不算)、`只剩小问题`、没有明确放行语句
- 「禁止表演性同意」是一份词面黑名单:`You're absolutely right!` / `Great point!` / `Thanks for catching that!`(还有 `Excellent feedback!` 和「让我现在就改」,`03:306-310`)
- P1 / P2 / P3 分级 + 「P1/P2 修完才能放行」也可判定(`03:177-186`)

这些不是 DSL,是**输出契约** —— 二十行 hook 就能执行,而 clowder 的 predicate 不能。

> **借契约的形状,不借它的住处。**
