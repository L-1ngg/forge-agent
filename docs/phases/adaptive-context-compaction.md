## What

### A. 状态与持久化

主要修改 `packages/core/src/context/`、`session-storage.ts`、`session-store.ts` 和 SDK 导出；不修改 runtime 的调度所有权。

- compaction 可选增强载荷含 `version: 1`、状态项、摘要结论及引用、保留消息 ID、文本裁剪记录、重建原因与增量次数；校验后原子追加一个检查点。首次增强压缩之前无增强载荷，仍可由原始历史构建。
- 状态项使用检查点内稳定 ID、类型、文本、`active/superseded`、来源 message ID 和原文片段；替代关系只允许引用同分支先前项。目标变更不默认删除仍有效的用户约束。
- 待归档用户消息原文和本次输入在提取成功之前不可移出。压缩摘要与结构化状态分开装配，均明确为历史资料，不能提升成 system 指令。
- 工具调用及结果的状态根据实际消息导出；缺结果为 unknown，不推断未执行。验证记录保存工具结果引用，模型对“任务已完成”的判断标记为推断，不能伪装成测试证据。
- 增强记录校验所有 ID 的分支归属、顺序、角色、引用片段、状态替代图及投影合法性。未知增强版本拒绝该视图；v4 无增强记录继续可读。
- 配置从 adaptive 切至 pi 时使用当前新 reader 的降级 summary 与合法近期后缀；重新启用 adaptive 从原始分支重建，不能信任 pi 摘要补出未存状态。保留历史，不原地转换旧文件。

### B. 请求材料选择

主要修改 `context/` 和 `AgentSession` 的请求准备接合，不增加第二条执行路径。

1. 收集当前分支、关键状态、待归档用户原文、当前完整交互单元、可选旧单元及固定 system/tools。
2. 去重限定同一正文与相同工具语义，不能合并两次不同执行结果。已记录工具结果可裁剪正文并附原文引用，结果状态和调用参数保持可解释。
3. 保护层包括 active 状态、待归档输入及最新工作单元；保护层超预算时失败，不静默删状态。
4. 可选层排序：状态直接引用优先，其次当前任务文本与材料的词项重合度，再按时间由近及远，稳定 ID 作最终平局规则。中文词项使用字符 bigram，英文使用小写词项；这是启发式，收益必须经评估验证。
5. 选中单元按历史顺序装配。工具调用/结果必须完整；无需保留已省略单元的整段原文。图片保留的原文单元继续按现有协议发送，被省略图片只能报告其存在，本版不声称视觉内容已总结。

### C. 原文找回

新增内核工具 `read_context`，输入为 `entryId`、从 0 开始的 `offset` 和 `limit`；offset/limit 单位为 Unicode code point，默认/最大 limit 为 4096，正文 UTF-8 不超过 16 KiB（元数据另计入请求预算）。输出包含角色、记录 ID、结果状态、文本和 `nextOffset`，到达结尾时无下一页。按已保存消息 text blocks 的固定顺序、以换行连接得到稳定可分页文本；图片仅返回占位说明，不声称读取图像语义。长 JSON 单行也可逐页读到尾部，不截断 Unicode code point；每个非末页 nextOffset 必须严格增加。

- 只查询当前选中分支中已保存的 message，不读取摘要中的伪造路径、不枚举其他会话。
- 使用现有 tool hooks、权限判定和取消信号；工具名冲突在配置应用前报错，旧配置保持。
- 工具结果与其他工具相同保存，归入预算；找回不触发原工具重跑。运行时稳定读取已完成记录，新配置/分支不改变当前工具批次的归属。
- 实施同步 SDK 中英文指南，说明自定义权限规则需允许该工具；未获准时准确报告 denied，而不是承诺原文一定可读。

### D. 提取、重建与预算

状态与叙述由一次结构化摘要请求共同返回。响应必须通过 JSON/schema、来源与状态图校验，摘要结论各自带来源列表；失败不发布。仅引用 assistant 的 fact 保守降为 inference，避免将模型报告升级为验证证据；保存后的载荷必须已经规范化。使用现有主模型、路由、摘要推理与临时错误重试分类，不新增模型依赖。

拟定默认值（仅 adaptive）：

| 项 | 选择 |
|---|---|
| 策略 | 初次交付默认 `pi`，显式 `adaptive` 启用增强行为 |
| 近期目标 | 沿用 `keepRecentTokens`，它是可选材料目标，不允许挤掉保护层 |
| task 输出预留 | 显式 maxTokens 优先；未指定时 adaptive 显式发送 min(4096, 模型正的 maxTokens)，pi 仍沿用 provider 默认。上游默认可占满剩余窗口，不适合作为增强策略的固定预留；发送与预算共享该值，并计入 provider 的额外 thinking 预算 |
| 额外空间 | `max(reserveTokens, effectiveMaxTokens + safetyMargin)`；safetyMargin 为 `max(1024, ceil(W * 0.02))` |
| 摘要输出 | `min(4096, 模型正的 maxTokens, floor(W * 0.2))`，至少 1；输入含摘要 system/schema/历史/旧状态，独立计量 |
| 压缩调用帽 | 每次压缩操作最多 4 次实际模型请求，包含临时重试；最多 2 次逻辑生成（初次＋一次重建） |
| 重建触发 | 第 4 次增量更新改为原文重建；有来源的明确任务切换或结构化矛盾也触发 |
| 无进展 | 候选投影估算未减少，或仍不满足下一次请求可用输入预算；只允许剩余额度内一次重建，否则 error |
| 超大重建 | 输入预检不通过则明确 `summary_input_budget_exceeded`；不做通用分块层级总结 |

两阶段提取中的已使用调用和 retry 共用计数，第二阶段不能重置额度。返回结构无效不当作临时服务错误盲目重试；如有额度，可用唯一重建阶段从原文重新请求。发布时只有候选完整且预算通过才追加记录，失败不改旧有效视图。

自动路径在预算不足时先低成本选择；足够时零摘要调用。不足再提取/重建；最终失败阻止该次过预算 task 请求，报告错误。手动路径同样有界，不在结束后自动续跑。显式 overflow 继续遵循一次恢复链，取消不启动新请求，保存失败停用。

预算以实际请求内容为准，输出预留不与输入混淆；字符估算与有效 usage 的来源在事件区分。所有新材料包括 read_context 工具 schema、引用封套和状态文本计入预算。提供下一步已知输入即可，不预测未知工具输出。

### E. 可观察性与 API

扩展现有 context 设置、compaction 结果和事件，保留旧字段；新字段包含策略、触发/重建原因、前后计量及估算属性、有效预算、逻辑生成/真实调用次数、合计 usage、耗时和停止原因。重试失败的已发生调用也必须计数。

SDK/CLI/TUI 使用相同 SessionEvent；已有 notice 能表达失败时不新建复杂交互。对新增工具检查配置更新、冲突及缓存计量失效。#30 若先合入，摘要/重建与重试接入同一宿主准入边界。

## Test plan

### 软件合同

沿用 Issue 已确定的公开 SDK 场景边界：`createAgent`、`runTurn/continue`、`compact`、持久化后重开、公开事件，加本地 HTTP provider 捕获请求和计数工具。先例为 `runtime-context.test.ts`、`compaction.test.ts`、`context-http.test.ts` 与存储分支测试。存储损坏/兼容可使用现有 SessionStore 公开边界；不为排序器新增专用测试接口。

必须覆盖：连续四次以上压缩、用户纠正、分支切换、失败摘要不发布、坏引用/原文片段不匹配、超 16 KiB 单行末尾及 Unicode 原文分页找回、unknown 执行状态、工具权限拒绝、取消与保存失败、输出上限改变、模型切换计量失效、状态自己放不下、summary 输入超预算、无进展停止和旧 reader 降级边界。

反向验证至少分别移除受保护约束、放开分支限制、制造重复工具调度、取消调用帽，确认对应场景失败；所有临时故障注入恢复后再做正式检查。结构测试不声明能证明语义忠实。

### 模型质量与性能

不把受控 HTTP provider 当真实模型评估。冻结 12 个任务：6 个开发集、6 个独立保留集；每集各包含长日志、用户纠正、连续压缩、证据精确查找、已执行副作用及任务切换。生成受控历史只初始化场景，随后任务与摘要使用真实 provider。

每个任务、每种策略重复 3 次，总计 72 次任务运行。固定同一模型 ID、provider、system、tools、初始历史和窗口/输出设置；按记录的确定性交替顺序交错策略（非随机抽样）。先在开发集调试，冻结参数后仅一次正式使用保留集；若依据保留集调参，换新保留集后重跑。记录 fixture 和实现 SHA、配置、实际运行顺序、provider 返回模型标识、每次调用 usage、各阶段耗时与逐任务输出。

评分规则预先定义在 fixture 中：最终产物/答案是否满足原始要求、应保留决策/约束、应该发生的副作用次数、需返回的原文事实。产物和调用次数用确定性检查，语义忠实使用隐藏策略名称后的独立人工/审阅判断，分歧保留依据。审阅 Agent 不担任实现质量的唯一事实来源。

初次验收门槛：

- 所有保留集 adaptive 运行无硬约束违反、无重复/错误副作用；失败实例不能被平均值掩盖。
- adaptive 保留集任务完成数不低于 pi；要求读取历史的成功任务应返回正确原文事实及有效引用。
- 报告状态保留、证据找回成功/额外读取、总 Token（含所有摘要、重建、失败重试）、压缩耗时和总任务耗时的中位数/p95，以及再次超限次数。
- 不要求成本和质量同时严格优于基线；若 Token 或任务耗时中位数增加超过 25%，保留显式 opt-in 并在验收结论中说明收益/代价，不能宣称整体性能提升。初次交付无论结果如何均不更改默认 pi。
- 小样本结果只支持该任务集和模型配置，不声称统计显著或全模型有效。物理窗口超限、其他 provider/OS 未测项独立标记。

运行前确认现有可用模型配置并冻结精确标识；先跑一个开发任务估算成本，整轮请求硬上限 2000，实际额度最多 USD 10（计价未知则在估价完成前不批量运行）。达到上限停止并保留已发生费用与未完成项，不能把未完成验收改成通过。

## Acceptance / Release

AC 原文只在 Issue #31；交付证据按 AC 编号映射。依次完成相关单文件测试和常规 typecheck，最终一次 `bun run check` 与 `bun run typecheck:examples`；新测试/脚本额外入口纳入既有工具链，不覆盖用户正在修改的 package.json。

运行 `/code-review` 两轴并行审查，输入起始 SHA、本任务文件/hunks、完整 WIP 及初始用户变更记录。修复可行动问题，对改动重验并刷新审查输入。只暂存已审查的本任务改动，检查 staged diff 后提交当前分支；push 后核对本地/远端 SHA 和 CI。完成真实模型验收、发布证据且无未解决 AC 才关闭 Issue。

不作为验收通过的证据：仅代码静态阅读、压缩率、受控摘要措辞、降低本地窗口触发、过去其他功能测试通过。缺少凭据或额度只说明真实验收未完成，不自动豁免。

## Rollback

初次增强行为 opt-in，配置切回 `pi` 可停止后续增强压缩；同版本 reader 使用保存的降级 summary，原始记录可从原分支重建。增强载荷持久化后不承诺降级到旧二进制保持相同投影；必要时在独立副本中导出原始消息，不覆盖原件。不在回退时重放工具。
