# ADR-010: 输入归属、执行干预与提交边界

> 状态:已批准(2026-09-05)。代码实现与自动化验收完成,待 operator 交付审核;证据见文末。
> 参与者:operator 提出体验问题并要求记录方案,Codex 调研与起草。

## 背景

operator 在 SDK review 后指出:“但是这样对于用户体验会不会比较坏呢？我想请你调研一下codex/claude code等产品在这个问题上的决策”。随后要求:“可以，你把这个ADR记录一下，然后我确认你的方案”。

2026-09-05 对 `d2519aa` 之后 SDK 工作区的审查复现了两个状态窗口:

1. `AgentRunner` 等待异步 `appendTurn()` 时,执行内核已经结束。SDK 仍允许 `steer()` 入队,但 `abort()` 无法清除该输入,它会进入下一次 invocation。
2. `HostedAgent` 在获取 iterator 时占用实例,底层运行却在第一次 `next()` 时才启动。在两者之间调用 `abort()`,随后仍会执行并提交任务。

相关路径为 `packages/core/src/agent.ts`、`agent-runner.ts` 和 `execution-core.ts`。当前 `agent_end` 只代表模型/工具执行结束,正常完成整个异步迭代才代表提交完成。将提交等待直接变成用户无法发送消息的窗口,会把内部存储时序暴露给用户。

本决策补充 [ADR-009](009-self-owned-agent-core.md) 的取消与队列边界。核心问题是输入归属与行为确定性,而不是要求所有产品在停止时一律删除队列。

## 决策

### 1. 输入由宿主保留,执行层只接收有明确归属的干预

- UI 在执行和提交等待期间都允许用户编辑、发送输入。暂时不能执行的输入进入宿主的可见队列,可以撤回或编辑。
- 宿主负责待发送输入与草稿,SDK/内核负责当前 invocation 已接受的 steering 和 follow-up。不同宿主可使用不同界面,不要求 SDK 启动 TUI。
- `steer()` / `followUp()` 只向仍可接收干预的当前 invocation 投递,不作为跨 invocation 的隐式邮箱。保留两者在活动执行中的时点区别与 FIFO 语义。
- SDK 明确反馈“已接受”或“当前执行已无法接收”。宿主收到未接受结果时保留原输入,根据用户意图排队或恢复草稿;不要求用户重新输入。
- 迟到的干预不能静默命中新 invocation。实现需绑定调用归属或提供等价的原子检查,不强制引入公共 Run/Step 模型。
- 接受干预与结束接收之间需要明确的原子边界,不能先通过检查再把消息放入已经停止消费的队列。具体返回类型与内部同步方式在施工图确定。

### 2. 用户界面采用以下默认规则

| 场景 | 行为 |
|---|---|
| 活动执行仍能接受干预 | 宿主选择 steer/followUp 时投递到当前 invocation,并跟踪是否已被处理;TUI Enter 沿用现有跨 invocation FIFO |
| 当前执行已结束,正在提交 | 保留为宿主可见队列;提交成功后按 FIFO 启动后续 invocation |
| 普通停止 | 停止自动发送,取消当前可取消执行;未处理输入恢复为草稿,由用户决定是否重发 |
| 停止并发送指定输入 | 停止旧任务的自动续发并等待收尾,成功后只发送用户明确指定的输入;其他待发送内容保留为可恢复草稿,不自动执行 |
| 提交失败 | 保留待发送内容并暂停自动执行,提示宿主核对存储与重建实例;恢复后由用户或宿主明确继续 |

普通停止后的草稿应保留文本、顺序及已有附件信息,不能因合并展示而丢失内容。已经处理的输入不恢复为待发送内容,避免重复执行;具体确认点与 UI 展示在施工时锁定。

这里选择恢复草稿的默认行为,没有采用 Claude Code 的 `Esc` 后继续自动发送队列策略。`abort()` 是执行控制,草稿恢复由宿主完成;SDK 调用者无需具备输入框。

### 3. 提交开始后不承诺取消存储

- 保留 `SessionStorage.load()` / `appendTurn()` 的最小接口,不增加事务取消、自动重试或补偿写入。
- 进入提交前取消,仍遵守整次 invocation 不提交的既有契约。提交入口与取消判断必须有确定顺序。
- `appendTurn()` 已开始后,`abort()` 无法保证阻止持久化,也不能把最终成功提交误报成回滚成功。宿主仍可停止后续自动发送并保留输入。
- `dispose()` 拒绝后续执行,等待活动执行清理或已开始的提交结算;不能声称强制撤销任意宿主工具或存储操作。
- `agent_end` 继续仅表示模型/工具执行终止;正常迭代完成才表示 invocation 完成。SDK 需使宿主能够正确处理干预未接受与提交失败,不要求 UI 展示“提交中”的实现术语。
- 提交失败继续停用实例,由宿主核对真实存储状态、重新创建并加载;不假设异常意味着未写入。工具外部副作用不会回滚。

### 4. 尚未启动的执行也有确定取消语义

如果 SDK 已占用实例并拒绝其他 invocation,该 invocation 即必须可取消。获取 iterator 后、第一次 `next()` 前调用 `abort()` 应保证后续不启动模型、不执行工具、不提交,并在关闭收尾后允许实例复用。不能出现 SDK 认为忙碌而取消路径认为空闲的状态。

## 被否方案

| 方案 | 不采用的原因 |
|---|---|
| 提交期间禁止用户输入或要求重发 | 用户无需理解存储窗口;正常输入应由宿主保留 |
| 所有输入直接进入内核全局队列 | 归属不清,迟到干预或取消后的残留可能进入新任务 |
| 只拒绝底层干预,不提供宿主保留机制 | 可以防止误投,但会丢失用户意图或增加重复输入 |
| 普通停止后自动发送全部剩余输入 | 不符合本项目本次选择的“停止自动执行、恢复草稿”语义 |
| 停止时删除所有未处理文字 | 执行取消不应意味着用户草稿丢失 |
| 照搬 Codex rollout 重试或承诺取消任意提交 | 本项目允许宿主自定义存储,没有足够的事务与幂等性保证 |

## 后果与施工边界

本方案把输入体验与执行安全分层:底层可以拒绝不再属于当前执行的干预,用户仍能顺畅地发送和取回输入。代价是宿主要跟踪待发送与已处理的区别,并处理普通停止、指定重发及存储故障。

现有 `packages/tui/src/app.ts` 已有独立 `queued` 队列,应沿用其结构按需补齐行为。SDK 不另建跨 invocation 的第二套自动调度器。不得借此扩展到 Team、持久消息队列、数据库重写或 TUI 美化。

配套施工与接入契约:

- [SDK 施工图](../phases/sdk.md):修订原“保留两条 FIFO 队列”的适用范围,定义接收确认、提交边界和未启动取消;重新验收受影响的 AC-SDK-02/04/05/06。
- [SDK 接入说明](../sdk.md):修订“取消不提交”的适用阶段,记录宿主队列、停止和提交失败策略。
- [自研内核施工图](../phases/owned-core.md):区分取消后清理内核队列与宿主恢复草稿,保留活动执行内的 steering/follow-up 顺序。

本决策收窄既有“取消不持久化”契约至提交开始前;此前自动化记录保留为历史证据,不代表本方案已验收。具体 API 与确认点见 SDK 施工图。

## 验收

- [x] AC-INPUT-01:慢存储提交期间,UI 接收并显示新输入,SDK 不向结束的执行队列投递;提交成功后仅按宿主队列顺序执行。
- [x] AC-INPUT-02:普通停止在模型流、工具执行及提交等待期间均停止自动续发;未处理输入可恢复且不会隐式混入新任务。
- [x] AC-INPUT-03:停止并发送等待旧任务收尾,仅自动执行指定输入;其他草稿不丢失,提交失败时不自动启动新任务。
- [x] AC-INPUT-04:干预与执行结束交错时,输入恰好被当前 invocation 接受一次或退回宿主;迟到干预不影响新 invocation,无丢失或重复执行。
- [x] AC-INPUT-05:iterator 已占用实例但未 `next()` 时可取消,零模型调用、零工具执行、零提交,关闭后可复用。
- [x] AC-INPUT-06:提交开始前取消不调用存储;提交开始后的停止/释放等待结果,不伪造回滚;失败仍停用实例并保留宿主输入。
- [x] AC-INPUT-07:核心故障注入、SDK 生命周期、TUI/PTY 端到端和完整检查通过;证据包含至少一次对应失败路径的反向验证。
